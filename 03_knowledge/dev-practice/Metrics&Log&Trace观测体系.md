在现代分布式系统的可观测性（Observability）体系中，Metrics、Log、Trace 被称为 "三大支柱"，它们从不同维度刻画系统运行状态。

## 核心定义对比

|维度|Metrics（指标）|Log（日志）|Trace（链路追踪）|
|---|---|---|---|
|**本质**|可聚合的数值型时序数据|离散的文本事件记录|一次请求跨服务的调用链|
|**数据形态**|时间序列（timestamp + value + labels）|结构化 / 非结构化文本|由多个 Span 组成的有向树|
|**回答的问题**|"系统现在怎么样？"（What）|"发生了什么？"（What happened）|"请求经过了哪里？为什么慢？"（Where & Why）|
|**典型粒度**|聚合后的统计值|单条事件|单次请求|
|**存储成本**|低（高度压缩）|高（原始文本量大）|中（采样后可控）|
|**查询方式**|PromQL、聚合函数|全文检索、关键字过滤|TraceID 关联、依赖分析|

## 各自详解

### 1. Metrics（指标）

对系统行为进行**数值化、聚合化**的度量，例如 QPS、P99 延迟、CPU 使用率、错误率。

- 特点：数据量小、查询快、适合做告警和大盘
- 典型工具：Prometheus、InfluxDB、Grafana、OpenTSDB
- 字节内部对应：Metrics（基于 ByteTSD）、Argos

### 2. Log（日志）

程序运行过程中产生的**事件记录**，包含上下文细节，是排查具体问题的最后一公里。

- 特点：信息最丰富，但量大、检索慢、噪音多
- 典型工具：ELK（Elasticsearch + Logstash + Kibana）、Loki、Splunk
- 字节内部对应：TLB（日志服务）、ByteLog

### 3. Trace（链路追踪）

记录一次请求在**分布式系统中跨服务、跨进程**的完整调用路径，每段调用是一个 Span，所有 Span 通过 TraceID 串联。

- 特点：揭示服务依赖、定位慢调用、分析瓶颈
- 典型工具：Jaeger、Zipkin、SkyWalking、OpenTelemetry
- 字节内部对应：Trace（基于 OpenTelemetry 协议）

## 三者关系

plaintext

```plaintext
        ┌─────────── 告警触发 ───────────┐
Metrics ────────► 发现异常（延迟突增）
                        │
                        ▼
   Trace ────────► 定位慢在哪个服务/接口
                        │
                        ▼
    Log ─────────► 查看具体错误堆栈与上下文
```

简言之：**Metrics 用于发现问题，Trace 用于定位问题，Log 用于诊断问题**。三者互补，共同构成完整的可观测性闭环。OpenTelemetry 已成为统一三者采集标准的事实规范。


# Metircs
Counter 记"次数"、Store 记"当前值"、Timer 记"耗时分布"。 三者对应三种完全不同的指标语义，在监控平台（如 ByteDance 的 Argos / Grafana）上能查询、聚合的方式也不一样。
## Counter
### 含义
累加型 指标。你每次调用，就把 value 加到"这一秒钟（或当前聚合窗口）这个指标的累计总量"上。监控平台看到的是类似 sum/rate 的曲线——常见图形是 QPS、请求总数、错误数。

### 典型使用场景
- 接口调用总次数 / QPS
- 成功 / 失败 / 超时次数
- 业务事件次数（比如"用户点击发送消息"）
- 缓存命中 / 未命中次数
## Store
### 含义
快照型/瞬时值 指标。每次调用 = "当前这一刻的值是多少"。监控平台上看到的是数值曲线，能上能下，通常查询 last/avg/max/min 。

### 典型使用场景
- 当前在线连接数、活跃会话数
- 队列长度、待处理任务数
- 内存占用 / goroutine 数量
- 连接池使用率
- 缓存大小（key 数量、字节数）

## Timer

### 含义
分布型 指标，专门记一段"耗时"。底层 SDK 会把一批上报的时延计算 分位数（pct50/pct90/pct99/max/avg） 并上报，这是和 Counter/Store 最大的不同。

在监控平台看到的通常是：

- avg ：平均耗时
- pct99 ：99 分位（99% 的请求比这个快）
- pct999 ：更极端的长尾
- max ：最大值
### 典型使用场景
- HTTP/RPC 接口耗时
- DB 查询耗时、Redis 调用耗时
- 下游依赖耗时
		- 业务流程里某个关键步骤的耗时
