# 引子：你每天调的那个 API，本体是什么

先做一个祛魅：一个能写代码、能讲笑话、看起来无所不知的大模型，它的「本体」是一个文件。以 Llama 3 70B 为例：一个 140 GB 的权重文件，里面是 700 亿个浮点数（FP16 半精度，每个数占 2 字节），按矩阵组织。除此之外只需要几百行推理代码——没有数据库，没有知识图谱，没有 if-else 规则库。

这个文件参与的唯一计算，是一个纯函数：输入一串 token（分词后的文本），输出「下一个 token 是词表中每个词」的概率分布。仅此而已。所谓生成一段回复，就是把这个函数放在循环里跑几百上千次，每次采样出一个词、拼回输入、再算下一个：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=MmZiMmQyYjY0OTNmMzU0NzYwZmQxOTk4MjA1ZDI2ZGRfc3VSNnpwS3lXUThZRUxpZnVhSHNFSXVod2hKaVdmV3pfVG9rZW46RTMycWJkNnB5bzVNRlh4aXdlcWxoemNMZ2RkXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

对后端工程师，这张图里有三个值得记住的事实：

- **它是无状态的。**模型不「记住」任何对话——权重不保存任何会话状态；常见 API 形态是客户端每轮把完整历史重新传入。这和你写的无状态服务是同一个设计：session 外置——外置给调用方，或由服务端会话层代管。
    
- **它的结构极其规整。**70B 模型是 80 层结构完全相同的 Transformer 层堆叠，每层就是几个大矩阵乘加一个 Attention 交互。没有 if-else、没有递归，从输入到输出的计算路径完全固定——这是 GPU 喜欢它的原因，也是后面一切性能优化的前提。
    
- **它很大。**BF16 权重 140 GB，放不进单张 H100（80 GB）；即便 H200（141 GB）、B200（192 GB）这类新卡装得下权重，KV Cache 与运行时开销仍要另留显存——生产部署照样绕不开多卡。「大」是全部工程复杂度的唯一来源：**训练时放不下，推理时搬不动**。
    

于是问题只剩两个：这 700 亿个数字是怎么被调到「会说话」的——训练；这个函数怎么跑得又快又便宜——推理。下面分两篇讲。

# 上篇 · 训练：把 700 亿个数字调对

## 三段式教育：预训练、SFT、强化学习

训练的目标只有一个：找到一组参数，让「下一词预测」尽可能准。完整流程分三步，数据量和算力相差好几个数量级：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=ZTVhMTE5NzEyYjVkNTI3ZjFlZTMxMGFhMDE3ZDY4MTdfeHhPbW1aaUFTQnEyUXBUOUVwN09iMzludTJpenczM0ZfVG9rZW46UVBKMWJDR1RWb2NsVWh4dHR6ZmxKOERZZzFnXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

预训练是重头戏，思想简单到不可思议：把互联网文本（约 15 万亿 token）全部过一遍，每个位置做一次「完形填空」，猜错就微调参数。妙处在于**标注是免费的**——下一个词本身就是标准答案。而要把代码续写对，就被迫学会语法；要把推理题续写对，就被迫学会逻辑。某种意义上，**压缩即智能**。

但预训练完的 base 模型只是个「接龙机器」：你问「北京有什么好玩的？」，它可能回「上海有什么好玩的？」——语料里问题列表后面跟着问题列表，这么续写毫无毛病。让它像个助手，靠后两步小数据量的整形：**SFT** 用几十万条人写对话教会「对话」这个格式；**RLHF** 让人类给回答排序、练出打分模型，再用强化学习照着优化。近两年的推理模型用的是第三步的变体 **RLVR**：用数学、代码这类可自动验证的任务当奖励，让模型学会「先想后答」。公开管线里最纯粹的是 DeepSeek-R1-Zero（纯规则奖励 RL）；完整版 R1 是 SFT 与 RL 交替的多阶段流程；o 系列只公开了「大规模强化学习」，细节未披露。

这里停一下，澄清一个常见误解：「预训练只教会了续写」——续写只是**考试形式**。要把「254 × 13 =」续写对就必须会算术，要把侦探小说的结局续写好就必须完成推理；把续写做到极致，学到的是语言、知识和推理本身。更准的说法：**预训练造出一个功能齐全但没有 API 文档的函数库，SFT 和 RL 只是包了一层好用的调用接口**。旁证是 LIMA 论文：仅 1000 条精选对话做 SFT 就得到合格助手——能力若非早已在库里，一千条数据教不出来。

## 预训练具体是怎么做的：一条 ETL，一个循环

三段教育里，**预训练一段占了 95% 以上的成本**，值得把黑盒单独拆开看——拆开你会发现没有黑魔法，它就是两件后端工程师最眼熟的东西：**一条超大规模的数据管线（ETL），加一个跑几个月的批处理循环**。

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=ZjY0OWM2NDMwYmNhZjk1ZTMxZWIxZGViMzhlYzBkODhfaEp4TXF4dzlwZ2pHSWVGNlZOeVhrbjlBN1AxSHNxa3FfVG9rZW46SzZ3ZGJnempyb1BkaDN4Z0puRGxTd0ZoZ1FnXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

先看数据侧。以公开复现 FineWeb 为参照：15T 量级的 token 要从 CommonCrawl 的 PB 级原始网页里过四道工序才能拿到，**留存率约 1%**。最有意思的是质量过滤：用大模型给样本打分、蒸馏成便宜的小分类器再去筛全量——用 AI 造 AI 的原料。清洗完还要定**配比**（Llama 3 公开配方：通用 50%、数学 25%、代码 17%、多语言 8%）：这个比例直接决定模型「性格」，是各家真正的机密。

再看训练侧。循环本体简单到令人失望：取 batch → 前向：用交叉熵给「猜得有多离谱」打分 → 反向：算出每个参数「该往哪拧」（梯度）→ 优化器拧一小下，重复约一百万步。工程智慧全在循环外（见图）：超参先用小模型扫描再外推、长上下文放最后练、收尾用最高质量数据退火。全程监控的主心骨是一条 loss 曲线（外围还有梯度范数、吞吐、MFU、评测这些仪表）：稳定下降就是岁月静好，突然跳升就按线上事故处理——回滚 checkpoint、跳过可疑数据、降学习率。

这条流水线本身没有黑魔法，难的是把它真正跑起来——绕不过去的问题只有两个，正好是预训练工程的两条战线。**原料**：15T 高质量 token 从哪来，互联网快挖完了之后怎么办？**产能**：一个状态 TB 级、一跑就是几个月的批处理任务，怎么摊到几万张随时会坏的卡上，还要摊得有效率？上篇剩下的内容就是这两条战线：下一节讲原料，其后四节（算力账 → 显存账 → 三种并行 → 容错）讲产能。

## 数据从哪来：当互联网不够用了

算力、显存、故障都有工程解法，训练真正的远期瓶颈是**数据**。全网高质量文本清洗完就是 15T token 量级，头部玩家已经基本用完——Ilya 的说法：「数据是 AI 的化石燃料」。而且自然数据「教学形态」差：网页上多的是结论，缺的是过程。业界的两条补给线：**蒸馏**和**合成数据**。

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=YWIyMmZiNWZjODk2ZjRmYTQ3MDMxYWUyYTE2NTdlMDBfcFVvRWQxQ295TFRlaW9FZEY5WGdZUldnS09FUzBRR1dfVG9rZW46SjdjRGJFM3dob1pjSFB4NGVzVGw3bG9aZ1FmXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

蒸馏的三种姿势按「能拿到多深的信息」分层（见图）。记住主流分工即可：**自家蒸自家是标准生产线**——先花大钱练旗舰，再用 logit 蒸馏冲压出一串量产小模型；**蒸别人家只能抄输出文本**——R1-Distill 用 80 万条样本（约 60 万条推理轨迹＋20 万条通用数据）做纯 SFT，就让 7B 底座学会「先想后答」。这再次印证前面的结论：能力一旦被练出来，就变成了可以用数据搬运的东西。

合成数据则把这件事推进到预训练：以真实网页为种子，让模型改写成 Q&A、教程等「高教学形态」，过五道质检后混入语料。整条管线就是一个数据加工平台（分桶、模板引擎、批处理、质检、灰度），且经济上成立——**造数据只花训练算力的零头**。

注意图底部的闭环：上一代模型跑在推理集群上，批量生产下一代的训练数据——**训练和推理，在这里咬合成了一个飞轮**。这个伏笔，读到下篇结尾你会再想起它。

## 三种并行：全是老朋友

1.12 TB 的状态怎么塞进一张张 80 GB 的卡？答案后端工程师闭着眼都能说出来：**切开，分片**。切法有三种，每一种都能在分布式系统教科书里找到原型：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=YzA5NTJiNTc2ODkzMjJlYTliYmZkYmMwOTBhYTY2OWRfVkhWczVPMXo3TnUzd0tqNERmNFU2MWZKMTFPQXhHQnhfVG9rZW46TnlMaWJwOVFrb1FlVk14aEtuNWxrTmFWZ3FoXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

三种并行的通信量差异极大，对应不同网络层级：TP 每层都要交换数据，通常优先放在机内 NVLink 域（900 GB/s）内，跨机虽可行但通信代价陡增；PP 和 DP 通信少得多，可走跨机 RDMA（400 Gb/s 量级）。所以典型部署是「机内 TP、跨机 PP＋DP」的组合（更大规模还会叠加 EP、CP、ZeRO/FSDP），怎么配最优取决于模型形状与集群拓扑——大厂有专门团队调这个，相当于分布式训练的容量规划师。

## 万卡集群的工程现实：平均 3 小时坏一次

到这里只解决了「能跑」。真正的难题是可靠性：Meta 训练 Llama 3 405B，1.6 万张 H100 连跑 54 天，如实记录了 **419 次意外中断**——平均 3 小时一次，78% 是硬件问题。单卡故障率不高，乘上一万六就是天天坏：万卡规模下，小概率事件就是日常。

应对手段你也熟：**checkpoint** 定期快照、挂了回滚重放，保存间隔是「算力浪费 vs 故障损失」的经典 trade-off。更阴险的是**静默数据损坏**（SDC）：某张卡悄悄算错但不报错，loss 慢慢发散，只能靠冗余校验和监控大盘抓出来。训练团队的日常，是把混沌工程当常态运营。

**上篇小结：**训练是一场「超级批处理作业」——数月、万卡、几十 TB 数据、千万美元，产出一个 140 GB 的文件。接下来的问题是：怎么用这个文件把钱赚回来。

# 下篇 · 推理：让它跑得又快又便宜

训练的开销集中在几个月的批处理里，推理是 7×24 的持续账单——模型上线之后，真正的账单在这里（财务口径当然没这么二分：自建集群有折旧、云上训练本身就是 OpEx、模型还要持续迭代，这里取的是工程直觉）。而理解推理优化的一切，都从看懂「一次请求的两个阶段」开始。

## 一次请求的两段人生：Prefill 与 Decode

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=ZTVmNmZkOTQ5MTg3MTQ2N2IxZTcwZWU4MjVhN2M2ZGVfTjV3Z2dnVHljd2FjODFQVDEwSTE0R2dIMmlaTWdKQjFfVG9rZW46U2ZxMWJnbU1Ub0xJS014S211ZGxPZFpEZ09lXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

两个阶段共享同一份权重，性能画像完全相反：**Prefill** 把整个 prompt 并行算完，矩阵乘又大又满，算力密集；**Decode** 一步一个 token，矩阵乘退化成瘦条，时间全花在搬数据上。SLA 相应拆成两个指标：**TTFT**（按下回车等多久）和 **TPOT**（吐字流畅度）。后面所有优化，都是在这两个延迟和吞吐（也就是成本）之间做交换。

## KV Cache：整个系统里最重要的一块缓存

上一节说 Decode 一步吐一个 token，这里藏着一个容易忽略的成本问题。Transformer 靠 **Attention（注意力）机制**理解上下文：每生成一个新词，都要回头「看一眼」前文的每一个词；而「看」用到的是每个历史词的两份中间计算结果——K 和 V。问题来了：这些 K/V，要不要每一步都重新算？

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=NjhiZTgyMWE5MTNlYWQxYjhjMGNjNmNlZTNlZjczZTJfTDI0QkFIU0hraklaYTFyU041eVpXSEdHcTcwTGFtQVRfVG9rZW46UUpXRmJTSzBhb1U4S1Z4ckZtOWxQcldDZzljXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

顺带一提，现代模型有个专为这块缓存做的设计：**GQA**（分组查询注意力），把 K/V 头数从 64 组压到 8 组，KV Cache 直接缩小 8 倍——没有它，上图的 40 GB 会是 320 GB。「为推理账单设计模型结构」如今是显学，MoE、MLA 动机都类似。

## 真正的瓶颈：显存带宽

现在可以回答一个关键问题：decode 阶段 GPU 算力大量闲置，那时间到底花在哪了？答案是搬运权重：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=MTc5ZjQzOGNkYTJmMTNkZmZkNzg5NzFiOTJlNmFhZDBfNEo4b1Z2SGFqSUNlcVFXQmtUMGpsQnpDZDVIUG4zOVVfVG9rZW46WEM0U2IzcmZpb1EyMkF4bUdGUmxRYXlFZ0NiXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

这堵「带宽墙」解释了推理系统的大量行为。比如**合批的边际成本极低**：batch 里多放几条请求，权重仍只搬一遍，闲着的算力顺手全算了——直到重新撞上算力瓶颈。量化和投机解码的动机也全在这。接下来三招，全是围着这堵墙打。

## 第一杠杆 · 合批：Continuous Batching 与 PagedAttention

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=NDNhODNlMzc2OWUwZDkzOWY0MGU3M2RhYjA5ZGU1NTFfdGZ5cXpVSHc3YWZ1OE9uR2RmalNNU0VBM09CM0U2UGRfVG9rZW46Vm9Hd2JBOGxZb2VWelJ4a3NNc2wxdXVjZ3JlXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

值得强调其中的 trade-off：batch 越大吞吐越高，但每个请求的 TPOT 会变慢（每走一步要伺候更多人），排队的 TTFT 也会拉长。生产系统做的是**在 SLA 约束下最大化吞吐**——这道题，你在线程池和消息队列的调优里已经做过一百遍了。

## 第二杠杆 · 量化：把要搬的东西变小

既然瓶颈是搬运体积，那就压缩它。量化 = 用更低的精度存储权重：

|精度|70B 模型体积|decode 速度|质量损失|
|---|---|---|---|
|FP16 / BF16（原生）|140 GB|1×（基准）|—|
|INT8 / FP8|70 GB|≈ 2×|几乎无损|
|INT4|35 GB|≈ 3~4×|轻微，对任务敏感|

收益直接来自上一节的公式：**体积减半，decode 上限翻倍**，还省下一半显存去开更大的 batch。代价是少量精度损失——GPTQ、AWQ 用几百条样本校准后多数任务损失轻微——但实际加速比与质量高度依赖 kernel、batch 和任务，表中数字当方向看，别当定律；KV Cache 也能量化到 8 bit。硬件在跟进：H100 原生 FP8、新一代 B 系列原生 FP4——算法和芯片合谋榨干每一个字节。

## 换模型的形状 · MoE：参数与算力解耦

三个杠杆都是运行时的优化，接下来是两台更大的手术——直接改**模型的形状**和**集群的形状**。先看模型。dense 的困境：每个 token 都要过全部参数——参数翻倍，训练算力和推理搬运也翻倍，**能力和成本锁死在一起**。但实践早就发现网络是稀疏激活的：处理代码和处理古诗，真正用到的参数高度不重叠。既然如此，何必每次全量跑？

MoE（Mixture of Experts，混合专家）的做法：把每层参数大头 FFN 替换成一群并列的小 FFN（专家），前面加一个叫 Router 的小打分层，**每个 token 只路由给得分最高的少数几个专家**，输出加权求和。Attention 部分保持 dense 不变：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=MDBlNmMzMjc5ZTM0MWJiNjBmNmJkODE3MDY5MDUwNWFfMXNoOXQ4Nm94eUtiejhoMjVtT1RiWlM2R0ZJUTVxZklfVG9rZW46TDFxYmJQWDVqbzdHNWR4bzRIeWxodmdSZ3BoXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

图中两个「代价」决定了 MoE 的部署形态。**显存不省**：任何专家都可能被点名，671B 必须全部常驻、单机放不下——于是必须**专家并行**（EP）：专家散布几十上百张卡，每层两次 all-to-all 把 token 递到专家所在卡再收回，这是集合通信里最难优化的模式。**路由是负载均衡问题**：Router 天然偏心，热点专家会把所在卡打爆——训练时加均衡约束逼它打散，推理时开多副本、动态重排，和你治理热点分片的手段如出一辙。

理解了这两条，就理解了为什么 MoE 成了近两年旗舰的主流路线——公开案例有 DeepSeek-V3/R1、Qwen3-MoE、Kimi K2（1T 总参、32B 激活）等，多数闭源旗舰的架构则未公开确认。在「同样的算力预算买最多的能力」这道题下，MoE 是当前的热门答案——代价是把复杂度从算力账单转移到了集群工程上。

## 换集群的形状 · PD 分离：把干扰拆开

前面讲过 Prefill 吃算力、Decode 吃带宽。跑在**同一张卡**上时，痛点是**干扰**：Decode 本来每步 30ms 匀速吐字，插进来一个 2000 token 的 prefill，这一步被拉到 200ms——批内所有用户同时卡顿；想保吐字流畅就得压 prefill，首字延迟又恶化。两个 SLA 抢一份资源，怎么调都是拆东墙补西墙：

![](https://bytedance.sg.larkoffice.com/space/api/box/stream/download/asynccode/?code=MjI2MzIxZGZlNDdmYmQ5N2E2YmJhYTQ5MWNmODkzMGFfTGROejNYUFpHZ2dJbGs0NktBcnI2TUs0eHFRTHlTUHlfVG9rZW46RzgxVmJkSkFFb3htVHV4WjlVZWxiQnc4Z1JXXzE3ODUzOTM3Mjc6MTc4NTM5NzMyN19WNA&add_watermark=true&scene_type=CCM&add_watermark=true&scene_type=CCM)

分家后两个集群可以**各自选并行策略、甚至各自选硬件**：Prefill 用高算力卡多切 TP；Decode 用大带宽大显存的卡开超大 batch——H20 算力打不过 H100 但带宽反超，做 decode 反而是天生神器，这就是它在国内推理市场吃香的技术原因。KV Cache 迁移账（640 MB / 13 ms）与一步 decode 同量级，还能逐层流水藏掉。效果：DistServe 论文同 SLA 下 goodput 最高提升 4 倍以上；Mooncake 真实线上多承接约 75% 请求。

当然它不是免费的：强依赖 RDMA 级互联（没有高速网络收益直接变负）、调度从一级变两级（选 P 实例、选 D 实例、还要考虑前缀缓存亲和性）、短 prompt 场景收益有限（prefill 本来就轻，多一跳反而亏，所以调度器通常保留合部署旁路）。

最后把两个主题合流：DeepSeek-V3 公开的推理实践正是「**PD 分离 ＋ 大 EP**」——prefill 单元 32 卡、decode 单元数百卡，每卡只摊一两个专家，省下的显存全给 KV Cache 和 batch。到这个形态，「部署一个模型」已彻底变成「运营一个分布式系统」——只是 SLA 的单位从毫秒变成了毫秒每 token。

# 终章：一张对照表，三句话

把上下两篇折叠成一张表：

|维度|训练|推理|
|---|---|---|
|**任务形态**|一次性超级批处理，数周~数月|7×24 在线服务|
|**核心指标**|MFU、训练稳定性|TTFT / TPOT / Goodput|
|**瓶颈**|算力 ＋ 集群通信|显存带宽 ＋ 显存容量|
|**状态**|训练态 ≈ 参数量 × 16 字节，TB 级 checkpoint|权重只读共享；KV Cache 按请求隔离、线性膨胀|
|**并行方式**|TP × PP × DP 三维组合|副本水平扩容 ＋ PD 分离 ＋ 专家并行|
|**故障应对**|checkpoint 回滚重放|重试摘流兜底（流式中断仍可感知）|
|**成本结构**|千万美元级的集中投入|OpEx：每百万 token 几毛到几十块|
|**最像什么**|超算作业|高性能在线服务|

最后，给后端工程师的三句话：

1. **瓶颈思维完全通用。**训练卡算力和通信，prefill 卡算力，decode 卡带宽，长上下文卡显存容量。先定位 bound 在哪，其余全是杠杆——这和你做性能优化的方法论一字不差。
    
2. **没有魔法，全是老手艺。**分片、流水线、缓存、分页、批处理、读写分离、容量规划——大模型 infra 的每一层都能在操作系统和分布式系统的教科书里找到原型。门槛不在新概念，而在把老手艺用到极致的工程密度。
    
3. **上手比想象中近。**找一张显卡用 vLLM 跑个 7B 模型，压测一下 TTFT/TPOT 随 batch size 的变化曲线，本文 80% 的内容你就有了体感。
