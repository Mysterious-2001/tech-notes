局限性

任务级递归：同一个任务会执行多次

任务到来后，Harness² 会用不同 Harness 重复执行同一个任务，通过执行差异判断修改是否有价值。

k=1 时大致需要 4 次任务执行：

用当前 Harness 执行一次，得到参考轨迹；
    
用通用型候选 Harness 执行一次；
    
用领域型候选 Harness 执行一次；
    
将有证据支持的改动组合后，再执行一次。
    


1.1.2
问题一：没有标准答案，怎样判断 Harness 修改是否更好？线上新任务往往只有需求、执行轨迹和交付物，没有可用于改进的 rubric、label 或 verifier
。
这里的没有标准答案不是说没有评测标准/GT，是说改进的过程是看不到GT的。
做一次对照实验。
Harness² 的 Composer 会看到：
任务要求和源材料；
原 Harness 的执行轨迹与交付物；
修改了什么；
候选 Harness 重跑后的轨迹与交付物。
所谓“有行为证据支持”，是指能够建立这条链路：
原执行出现具体问题 → Harness 加入针对性修改 → 重跑后对应行为发生变化 → 交付物更符合任务要求，且没有明显回归。


因此，运行时的判断依据本质上是：
轨迹是否修复了已观察到的执行问题；
交付物是否更符合任务的显式要求和源材料；
修改是否引入新的问题。


所以目前来说：检索一次任务只允许执行一次，并且线上 Harness 必须冻结，那么不应照搬 Harness² 的在线递归


1.1.2
问题二：当前任务的成功修改，怎样帮助未来任务？直接继承上一个任务高度定制的 Harness 容易污染新任务；完全不继承，又会让每次改进从零开始。
注意：这里的经验是对优化器如何优化的经验，不是对执行任务本身的优化经验



1.4.3
1. Compose 是什么？

Compose 是一个 Harness 合并与决策阶段，输出的不是答案，而是最终 Harness。

它会读取：

原始 Harness；
INV 候选及其试跑轨迹；
DOM 候选及其试跑轨迹；
每项候选修改造成的行为变化。

然后对修改逐项决定：

保留；
修改后保留；
删除；
或完全保留原 Harness。

例如，INV 候选增加“输出后重新打开检查”，DOM 候选增加“财务数据勾稽 skill”。如果两项在试跑中都有效，Compose 会将它们合并进最终 Harness，而不是简单选择其中一个。

2. Library 为什么叫跨任务经验？

这里的“跨任务”不是任意任务之间迁移，而是：

同领域的不同任务实例之间复用经验。

cue 描述的是可重复出现的问题模式。例如：

任务 A：合并预算表；
任务 B：合并招聘计划和人员名单；
共同 cue：多个文件使用不同字段表示同一对象。

两个任务不同，但共享同一种问题形态，所以历史经验可能适用。更准确的表述应是“同领域跨任务经验”。

3. 什么是“基于执行证据的改动整合”？

意思是 Compose 不只看修改内容，而是看修改后的实际试跑结果：

修改了什么 → Agent 行为发生什么变化 → 交付物是否改善。

例如：

增加回读检查；
试跑中 Agent 确实重新打开文件；
发现并修复了缺失工作表。

这就是支持该修改的执行证据。但它仍是弱证据，不能排除随机性或多个修改互相混杂。
