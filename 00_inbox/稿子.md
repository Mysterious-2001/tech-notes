## 局限性

### 任务级递归：同一个任务会执行多次

任务到来后，Harness² 会用不同 Harness 重复执行同一个任务，通过执行差异判断修改是否有价值。

`k=1` 时大致需要 4 次任务执行：

1. 用当前 Harness 执行一次，得到参考轨迹；
    
2. 用通用型候选 Harness 执行一次；
    
3. 用领域型候选 Harness 执行一次；
    
4. 将有证据支持的改动组合后，再执行一次。
    

  **问题一：没有标准答案，怎样判断 Harness 修改是否更好？**线上新任务往往只有需求、执行轨迹和交付物，没有可用于改进的 rubric、label 或 verifier。

这里的没有标准答案不是说没有评测标准/GT，是说改进的过程是看不到GT的。
做一次**对照实验**。
Harness² 的 Composer 会看到：
- 任务要求和源材料；
- 原 Harness 的执行轨迹与交付物；
- 修改了什么；
- 候选 Harness 重跑后的轨迹与交付物。
所谓“有行为证据支持”，是指能够建立这条链路：
> 原执行出现具体问题 → Harness 加入针对性修改 → 重跑后对应行为发生变化 → 交付物更符合任务要求，且没有明显回归。


因此，运行时的判断依据本质上是：

1. **轨迹是否修复了已观察到的执行问题；**
2. **交付物是否更符合任务的显式要求和源材料；**
3. **修改是否引入新的问题。**




所以目前来说：检索一次任务只允许执行一次，并且线上 Harness 必须冻结，那么不应照搬 Harness² 的在线递归

**问题二：当前任务的成功修改，怎样帮助未来任务？**直接继承上一个任务高度定制的 Harness 容易污染新任务；完全不继承，又会让每次改进从零开始。
注意：这里的经验是对优化器如何优化的经验，不是对执行任务本身的优化经验

| 时间       | 内容                          | 听众应该记住什么                    |
| -------- | --------------------------- | --------------------------- |
| 0–2 分钟   | 结论与 Agent = Model + Harness | 模型不变，Agent 能力仍可显著改变         |
| 2–6 分钟   | What：对象与问题                  | 它解决新任务、无 verifier、经验难迁移     |
| 6–12 分钟  | How：两层递归与 PPC               | 真实试跑提供修改证据，Library 学习以后怎么改  |
| 12–15 分钟 | Where it works              | 高价值长任务适合；低延迟和高风险正确性场景不适合直接用 |
| 15–19 分钟 | So What：结果、消融、案例            | 收益不只是堆算力，Harness 是独立性能杠杆    |
| 19–20 分钟 | 最终判断                        | 值得试点，但不是可放任的自进化系统           |
第二点，improvement library是啥，参考历史经验具体是怎么做的？怎么检索和加载历史经验的？

Improvement Library 不是模型参数，也不是向量数据库。它本质上是一个**按领域组织的历史改进文件库**，只提供给 Harness 编辑器
每完成一个任务，系统会保存：
- 最终采用的完整 Harness；
- `EXPERIENCE.md`，记录适用场景 `cue`、修改方法 `lesson`、执行证据 `evidence` 和置信度；
- `INDEX.md`，汇总历史任务、Harness 组件和 cue。
下一个同领域任务的使用流程是：
```
任务完成
→ 反思全部候选的修改与执行差异
→ 提炼可复用经验
→ 写入该领域的 Library

新任务到来
→ 加载该领域的整个 Library
→ 编辑器先阅读 INDEX.md
→ 根据 cue 判断哪些历史任务相关
→ 打开相应 EXPERIENCE.md 和完整 Harness
→ 复制或改写相关组件
→ 通过 Probe 在新任务上重新验证
```

关键点是：**当前实现没有向量检索、相似度排序或自动 Top-K。** 系统只是把同领域的全部历史 Library 复制到编辑器工作区，由模型阅读 `INDEX.md`，再自主打开它认为相关的条目。
例如，历史经验是：
> cue：任务需要合并多个字段命名不一致的表格  
> lesson：在 Harness 中加入“先建立字段映射、再执行合并”的 reconciliation skill
>新任务也出现多个异构表格时，编辑器可能打开这条经验，复制并调整对应 skill，再通过候选重跑验证是否有效。

所以这里的“参考历史经验”，实际是**模型驱动的文件浏览与组件复用**，不是成熟的检索系统。这也是它的局限：Library 变大后，相关性判断、冲突处理、过期经验清理都会成为问题。
**存储形式和检索方式基本就是 LLM Wiki**：

- 文件化存储：`INDEX.md + EXPERIENCE.md + 目录结构`
- 按领域分目录
- LLM 先读索引，再自主打开相关条目




1.4.3
### 1. Compose 是什么？

Compose 是一个 **Harness 合并与决策阶段**，输出的不是答案，而是最终 Harness。

它会读取：

- 原始 Harness；
- INV 候选及其试跑轨迹；
- DOM 候选及其试跑轨迹；
- 每项候选修改造成的行为变化。

然后对修改逐项决定：

- 保留；
- 修改后保留；
- 删除；
- 或完全保留原 Harness。

例如，INV 候选增加“输出后重新打开检查”，DOM 候选增加“财务数据勾稽 skill”。如果两项在试跑中都有效，Compose 会将它们合并进最终 Harness，而不是简单选择其中一个。

### 2. Library 为什么叫跨任务经验？

这里的“跨任务”不是任意任务之间迁移，而是：

> **同领域的不同任务实例之间复用经验。**

`cue` 描述的是可重复出现的问题模式。例如：

- 任务 A：合并预算表；
- 任务 B：合并招聘计划和人员名单；
- 共同 cue：多个文件使用不同字段表示同一对象。

两个任务不同，但共享同一种问题形态，所以历史经验可能适用。更准确的表述应是“**同领域跨任务经验**”。

### 3. 什么是“基于执行证据的改动整合”？

意思是 Compose 不只看修改内容，而是看修改后的实际试跑结果：

> 修改了什么 → Agent 行为发生什么变化 → 交付物是否改善。

例如：

- 增加回读检查；
- 试跑中 Agent 确实重新打开文件；
- 发现并修复了缺失工作表。

这就是支持该修改的执行证据。但它仍是弱证据，不能排除随机性或多个修改互相混杂。
