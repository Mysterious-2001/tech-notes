问题一：没有标准答案，怎样判断 Harness 修改是否更好？线上新任务往往只有需求、执行轨迹和交付物，没有可用于改进的 rubric、label 或 verifier
。
这里的没有标准答案不是说没有评测标准/GT，是说Harness 改进的过程是看不到GT的。
做一次对照实验。
Harness² 的 Composer 会看到：
任务要求和源材料；
原 Harness 的执行轨迹与交付物；
修改了什么；
候选 Harness 重跑后的轨迹与交付物。
所谓“有行为证据支持”，是指能够建立这条链路：
原执行出现具体问题 → Harness 加入针对性修改 → 重跑后对应行为发生变化 → 交付物更符合任务要求，且没有明显回归。


因此，运行时的判断依据本质上是：
轨迹是否修复了已观察到的执行问题；
交付物是否更符合任务的显式要求和源材料；
修改是否引入新的问题。


所以目前来说：检索一次任务只允许执行一次，并且线上 Harness 必须冻结，那么不应照搬 Harness² 的在线递归

1.2.1
1. Compose 是什么？

Compose 是一个 Harness 合并与决策阶段，输出的不是答案，而是最终 Harness。

它会读取：

原始 Harness；
INV 候选及其试跑轨迹；
DOM 候选及其试跑轨迹；
每项候选修改造成的行为变化。

然后对修改逐项决定：

保留；
修改后保留；
删除；
或完全保留原 Harness。

例如，INV 候选增加“输出后重新打开检查”，DOM 候选增加“财务数据勾稽 skill”。如果两项在试跑中都有效，Compose 会将它们合并进最终 Harness，而不是简单选择其中一个。

2. Library 为什么叫跨任务经验？

这里的“跨任务”不是任意任务之间迁移，而是：

同领域的不同任务实例之间复用经验。

cue 描述的是可重复出现的问题模式。例如：

任务 A：合并预算表；
任务 B：合并招聘计划和人员名单；
共同 cue：多个文件使用不同字段表示同一对象。

两个任务不同，但共享同一种问题形态，所以历史经验可能适用。更准确的表述应是“同领域跨任务经验”。

3. 什么是“基于执行证据的改动整合”？

意思是 Compose 不只看修改内容，而是看修改后的实际试跑结果：

修改了什么 → Agent 行为发生什么变化 → 交付物是否改善。

例如：

增加回读检查；
试跑中 Agent 确实重新打开文件；
发现并修复了缺失工作表。

这就是支持该修改的执行证据。但它仍是弱证据，不能排除随机性或多个修改互相混杂。

2. ### 从失败假设到经过执行验证的修改
    

从线上 Response、Trace、规则检查和用户弱反馈提供问题线索，现有五维评分帮助确定检查方向。

先形成失败候选，再通过 AFS 局部查证和同类样本确认、聚合为失败模式；但知识缺失等原因，需要与 Harness 问题区分。

归因分两步进行：

先只根据 Query、Response、用户要求和来源证据评价结果，再开放 Trace 调查原因。沿“原始工具结果 → 抽取后的 Observation → 模型实际输入 → 最终答案”检查信息在哪里丢失，减少合理的过程表述对质量判断的影响。

归因的产出进一步成为一项修改任务：

指出具体组件与规则，列出支持证据，提出根因假设，并预测修改后应该出现什么行为变化。例如，原始返回已有证据而抽取后丢失，候选就应针对抽取规则；规则已经进入模型输入但未执行，则需要继续调查条件、冲突或遵循问题。

Harness Editor 根据这项任务和相关历史经验，生成最小 Candidate Diff。

通用执行问题与特定场景问题可以分别提出 INV、DOM 候选，但都应围绕当前失败模式，说明修改理由和预期变化，不直接覆盖线上 Harness。

随后，通过实验 Scope 让 Base 与 Candidate 执行相同 Query，产生各自的 Response、Trace 和成本记录。Scope 提供候选接入方式，实验仍需固定实际解析后的 Harness、模型和预算，并记录知识与权限条件。历史 Trace 适合验证已有观察上的局部修改；改变选路或产生新命令后，需要真实执行相应检索。

对照同时检查两件事：预期的检索行为是否发生，答案质量与成本是否满足目标。行为未变，应重新检查修改与归因；行为改变却没有带来收益，则要继续判断这条路径的价值、噪声和成本。多个候选具有互补收益时可以 Compose，但组合版本必须重新执行。

结果比较延续同一评价顺序：Comparator 先匿名比较答案与来源证据，不看候选身份和 Diff，形成质量判断；再查看 Trace 解释差异。已有 GT 的样本沿用相应 Rubric，没有 GT 的样本根据证据支持、需求覆盖和事实一致性做相对判断，同时检查规则合规、调用量与延迟。

同一轮实验中固定检查标准，允许候选胜出、持平、失败或无法判断。AFS 局部查证可以发现遗漏和矛盾，但不能证明全库召回完整；证据不足时，保留结论边界。

3. ### 从当前 Query 改善到持续演进
    

同题对照解决当前问题，公共版本还需要接受跨 Query 检验。候选在当前 Query 上胜出后，继续用同类 Query 验证收益能否复现，用边界 Query 检查触发条件，用历史稳定 Query 检查已有能力是否退化。达到质量、约束与成本目标后，再进入灰度；出现退化则拒绝或回滚。

因此，Adopt 与 Promote 是两次不同决策：前者采用当前任务上的候选，后者在回归和灰度通过后更新公共 Base。修改的实际适用范围，应由这些实验结果共同确定。

每轮实验还要将问题特征、修改、预期与实际行为差异、适用范围和反例写入 Improvement Library。有效做法供下一轮参考，失败实验和不适用边界用于减少重复探索；经验与其对应的 Harness 版本、执行证据保持关联。

下一轮遇到相似问题时，归因和 Editor 先参考相关经验，再形成新的候选并接受验证。由此形成两个相连的循环：执行 Harness H 通过验证逐步改善，改进 Harness G 通过实验经验提高发现、生成和选择修改的能力。经验是否有价值，最终体现在后续候选质量、回归表现与试跑成本上。

这套体系中，归因负责形成有证据、可检验的修改假设，Editor 负责生成候选，实验执行与 Comparator 负责验证，发布流程负责晋升与回滚。各环节围绕同一失败模式和版本记录衔接，最终把一次问题处理转化为可追踪、可复用的改进。
