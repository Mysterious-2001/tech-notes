一句话：**ByteIO 是司内统一的流量/行为数据平台，负责把埋点从定义、采集、校验、加工到消费的完整生命周期管理起来。**

可以把它拆成两部分：

**控制面**

- 用 `app_id`/项目空间管理数据归属
- 定义 Event 和 Param 的名称、类型、含义
- 注册上报来源，例如 PSM、Caller
- 管理审核、上线、变更、下线
- 提供实时埋点验证和质量治理

**数据面**

```text
业务代码产生事件
  -> SDK 采集
  -> ByteIO 接收并校验
  -> 加工和分流
  -> TEA / Hive / Kafka / RMQ / 推荐系统
```

一条典型事件由这些部分组成：

- `User`：谁触发的，例如用户 ID、设备 ID
- `Header`：来自哪个应用、版本、平台、服务
- `EventName`：发生了什么
- `Params`：描述这个事件的业务维度
- `Time`：什么时候发生

**它和 Mario 的关系**

ByteIO 不是 Mario SDK。

- **ByteIO**：平台、事件规范、校验、数据加工和分发
- **Mario Collector**：把事件发送到 ByteIO 的服务端采集 SDK
- **TEA**：消费 ByteIO 数据，做事件分析、漏斗和看板
- **Hive/数仓**：沉淀明细、加工 DWD/DWS 和复杂指标

所以可以类比为：

```text
Mario Collector = 快递员
ByteIO = 物流中心 + 数据规范管理
TEA/Hive = 收到数据后的分析场所
```

对当前检索漏斗来说，ByteIO 承载的是“事实事件”：某请求召回了哪个文件、哪个文件进入了模型上下文。请求级去重、漏斗聚合和指标口径通常再由数仓或 TEA 完成。

它也不同于可观测体系：

- 日志：主要用于排障
- Metrics：适合 QPS、耗时、成功率等聚合监控
- Trace/Fornax：描述一次请求内部的调用链
- ByteIO：描述可长期分析的结构化业务事实

最重要的一点是：**ByteIO 不只是接收 JSON 的通道，而是一套先定义数据契约、再按契约采集和治理的系统。**事件没有在 ByteIO 中正确注册并上线，即使 SDK 发出了数据，也可能无法进入后续分析链路。
