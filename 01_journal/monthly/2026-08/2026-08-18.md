KV cache 不要每次改系统提示词

我的优化优先级是：

1. 合并 `context_extract` 和下一轮 `tool_plan`
    
    简洁模式其实已经这么做了：下一轮 planner 同时压缩上一轮结果，[代码在这里 (line 1029)](/Users/bytedance/company-project/smart_retrieval/service/react/orchestrator.py:1029)；lite 模式甚至完全跳过 extractor，[代码在这里 (line 1125)](/Users/bytedance/company-project/smart_retrieval/service/react/orchestrator.py:1125)。
    
    建议把这个机制推广到普通模式。两轮检索可从 6 次核心模型调用降到约 4 次，模型链路调用数减少约 1/3。它是当前最值得做的优化。
    
2. 不要所有阶段都使用 GPT-5.4
    
    `intent judge / task plan / skill select / context extract` 本质上多是分类或短 JSON 生成。经过评测后，适合切到更快的小模型；GPT-5.4留给复杂工具规划和最终回答。这个收益可能比 prompt cache 更明显。
    
3. 控制动态上下文
    
    当前 TCC 的 observation 上限达到 1000，`current_context` 会随轮次增长，而且它不可跨请求缓存。应改成按阶段设置 token budget、相关性 Top-K 和去重，而不是简单按条数放宽。
    
4. 调整 prompt 前缀以利用缓存
    
    不需要机械地把所有变量从 system 搬到 user。原则是：
    
    ```
    稳定规则/Skill 定义放最前
    动态 query/context/tool result 放最后
    ```
    
    每次都是新 HTTP 请求不会自动让缓存失效；GPT-5.4 的 Prompt Caching 可以跨独立请求复用完全一致的前缀。但目前几个 prompt 把动态上下文插在 system 中间，导致后面的静态规则也无法复用。[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
    
5. 缩短模型输出
    
    当前部分阶段 `max_output_tokens` 有 8192、甚至 30000。上限本身不会强迫模型输出这么长，但应该配合更短的 JSON schema、去掉冗长 reason，并按阶段压到合理范围。输出 token 往往比输入 token 更直接影响总耗时。
    
6. 先补齐监控，否则无法验证
    
    当前网关只记录整次 `duration_ms`，而且使用 `stream: false`：[model_gateway.py (line 191)](/Users/bytedance/company-project/smart_retrieval/common/model_gateway.py:191)。usage 也没有记录 `cached_tokens`：[model_gateway.py (line 304)](/Users/bytedance/company-project/smart_retrieval/common/model_gateway.py:304)。
    
    至少需要记录：
    
    - 每个阶段的调用次数和耗时
    - input/output/reasoning tokens
    - cached input tokens / cache hit rate
    - AFS 工具耗时
    - 每个任务的 Skill/Tool 轮数
    - TTFT 与完整响应时间

结论：有明显空间。最短路径是先推广“planner 顺便做上一轮结果抽取”，再做阶段模型降级和上下文预算；调整 system/user 位置属于第二梯队优化，不应先做。
