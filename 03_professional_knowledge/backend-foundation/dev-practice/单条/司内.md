# 上线流程
[1] 开发者 git push → 触发 SCM 流水线
        │
        ▼
[2] SCM 在构建机执行 build.sh
        │  └── atum deploy-with-scm
        │        │
        │        ▼
[3]            读取 atum.yaml
        │        ├── 拉取 python@v1 模板（python 3.9.0 基础镜像）
        │        ├── pip install -r requirements.txt（含 bytedance.fornax==1.0.35）
        │        └── 把 source: . 的代码打包成 SCM 产物
        │
        ▼
[4] 产物推送到 TCE / FaaS 平台 → 调度到容器
        │
        ▼
[5] 容器启动 → 执行 bootstrap.sh
        │  └── bytedunicorn 拉起 4 个 GeventWorker，每个 import server，拿 server.server 提供 thrift 服务
        │
        ▼
[6] server/__init__.py 顶层代码执行（每个 worker 各执行一次）：
        ├── monkey.patch_all()
        ├── logging.config.dictConfig(...)
        ├── init_default_client()              ← bytedance.metrics 客户端
        ├── init_fornax_tracer()               ← Fornax Trace 初始化（你刚加的）
        └── server = euler.Server(...)         ← 注册 runRetrieval handler
        │
        ▼
[7] 平台开始往 PORT 灌流量 → 每个请求进入 runRetrieval：
        ├── 解析 req.trace_info → parent_span_from_trace_info
        ├── start_root_span(child_of=parent)
        ├── agent_service.handle_agent_request(...)
        └── root_span.finish()
        │
        ▼
[8] 进程退出（缩容 / 重启 / max_requests 触发）：
        └── 当前实现：close_fornax_tracer 只在 main() 的 finally 里调用，
            但线上是 bytedunicorn 拉起的，不会走 main()，
            close_trace 实际不会被显式调用 ⚠️（见下方）

# 部署有关

代码仓 (Codebase)
   │ git push / merge MR
   ▼
BITS (流水线 / CI)
   │ 调用 build.sh → atum deploy-with-scm
   ▼
SCM (制品仓库)            ← 产出 1.0.0.157 这种版本号
   │ 制品打包好放这里
   ▼
TCE (运行时部署平台)       ← 自己有 install_package_info、有 pod、有部署 ticket


热部署/热更新是字节内部 BITS 提供的一种 快速迭代模式 ，但它有个非常重要的限制—— 只更新代码，不会重新装 pip 包 。



### 热部署够用 vs 必须全量部署
改动类型 热部署够用 必须全量部署 改 Python 业务逻辑 / 模板 / 配置文件 ✅ 加日志、改函数实现、改路由处理 ✅ 改 requirements.txt / TCE install_package_info ✅ 升级 / 降级已有依赖版本 ✅ 改 atum.yaml / bootstrap.sh / build.sh ✅ 改 Python 解释器版本（如 3.9 → 3.10） ✅ 改环境变量 / 容器配置 / sidecar ✅ 改 IDL（thrift/proto），需重新生成 stub 看产物在不在仓库；产物已 commit 就行 没 commit 要全量 改 C 扩展 / 二进制资源 ✅


### 热部署到底干了啥


看一下典型的字节"热更新"实现机制：

```
BITS 触发热更新
  ↓
向运行中的 pod 推送新版本代码（rsync / scp / 
volume mount）
  ↓
软重启业务进程（reload）：旧 worker 退出，新 
worker 起来
  ↓
新 worker 读新代码，但 site-packages 没动
```
关键点：

- pod 容器 没重建 ，所以 pip show xxx 看到的还是旧的依赖列表；
- install_package_info 是 TCE 在 容器拉起 时执行的，热部署不走这条路；
- "热部署完成"本质只是 reload 了 Python 进程
