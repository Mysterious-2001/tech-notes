**系统设计的判断框架 = 把一个模糊业务问题，拆成可设计、可权衡、可验证的工程问题。**

# **第一步：明确系统到底服务谁**

先问：

1. 用户是谁？
2. 用户最重要的动作是什么？
3. 系统失败时，谁受影响最大？

# **第二步：区分功能需求和非功能需求**

功能需求回答：系统要做什么？

非功能需求回答：系统做到什么程度？

以短链接系统为例。

功能需求：

- 创建短链接
- 访问短链接跳转到原链接
- 查询短链接统计
- 支持过期时间
- 支持自定义 alias

非功能需求：

- 跳转延迟低，比如 P99 < 100ms
- 高可用，比如 99.9% 或 99.99%
- 读远多于写
- 短链接不能冲突
- 数据不能轻易丢
- 统计可以延迟，不一定强一致

真正决定架构的，往往是非功能需求。
# **第三步：找核心数据**

系统设计逃不开数据。你要尽早问：

1. 系统里有哪些核心实体？
2. 每个实体的唯一标识是什么？
3. 数据之间是什么关系？
4. 哪些数据必须强一致？
5. 哪些数据可以异步或最终一致？

# **第四步：判断读写模式**

问：

1. 读多还是写多？
2. 读写比例大概多少？
3. 哪个操作是高频路径？
4. 哪个操作可以慢一点？
5. 哪个操作不能失败？

短链接：

- 创建短链：低频写
- 访问短链：高频读
- 统计分析：异步、可延迟

所以架构倾向：

- 读路径极致优化
- 写路径保证唯一性和持久化
- 统计路径异步化

聊天系统：

- 发消息：高频写
- 收消息：高频读/推送
- 历史查询：分页读
- 已读状态：高频但弱一致可接受

这和短链接完全不同，所以架构也完全不同。

# **第五步：估算规模，不要精确，要抓量级**

规模估算不是数学表演，而是为了发现瓶颈。

你至少估：

1. DAU / MAU
2. QPS
3. 峰值 QPS
4. 存储量
5. 带宽
6. 单条数据大小
7. 增长速度

短链接例子：

假设：

- 每天创建 100 万短链
- 每天访问 10 亿次
- 读写比约 1000:1
- 每条映射数据 500B
- 每条点击事件 200B

推导：

- 映射数据每天约 500MB
- 一年约 180GB，数据库能扛
- 点击事件每天约 200GB，一年约 73TB，不能简单塞进普通业务库
- 访问 QPS 平均约 11574，峰值可能 10 倍，约 10 万 QPS

结论：

> 真正大的不是短链映射表，而是访问事件流。跳转查询需要缓存，统计需要异步写入分析系统。

这就是估算的价值。

# **第六步：定义成功指标**

系统设计必须知道什么叫“好”。

常见指标：

- 延迟：平均、P95、P99
- 吞吐：QPS、TPS
- 可用性：99.9%、99.99%
- 一致性：强一致、最终一致
- 数据完整性：可不可以丢、可不可以重复
- 成本：机器、存储、带宽、人力维护
- 可演进性：未来能不能扩展

短链接：

- 跳转 P99 < 100ms
- 跳转服务 99.99% 可用
- 短链映射不能丢
- 统计允许分钟级延迟
- 点击事件可以少量重复，但最好不能大量丢

这会直接推出：

- 跳转服务要缓存
- 映射数据要持久化
- 统计要走消息队列
- 统计消费要支持幂等或去重


# **第七步：识别失败场景**

一个系统的设计质量，主要看它怎么面对失败。

你要问：

1. 数据库挂了怎么办？
2. 缓存挂了怎么办？
3. 消息队列积压怎么办？
4. 下游服务超时怎么办？
5. 重试会不会导致重复写？
6. 部分成功怎么办？
7. 用户请求中断怎么办？
8. 机器重启时数据会不会丢？

短链接跳转：

- 缓存 miss 时查 DB
- DB 慢时跳转变慢
- DB 挂了时，只能服务缓存里已有的短链
- 统计服务挂了，不能影响跳转
- 统计消息重复，计数可能重复，需要接受或去重

这个思考会让系统从“正常情况下能跑”变成“异常情况下还能活”。


# **第八步：做权衡，而不是追求完美**

系统设计没有银弹。每个选择都要能回答“为什么”。

比如短链接跳转要不要强一致？

如果用户刚创建短链，马上访问：

- 强一致：创建成功后必须立刻可访问，体验好，但写路径和读路径耦合更强。
- 最终一致：创建后可能延迟几秒可访问，系统更容易扩展，但用户体验差。

通常短链接创建后应该马上可访问，所以映射数据写入主库成功后，至少读路径能查到 DB；缓存可以异步预热，不要求必须先写缓存。

统计要不要强一致？

通常不要。因为统计不应该拖慢跳转。

这就是两个不同数据的不同一致性要求：

- 短链映射：强一致倾向
- 点击统计：最终一致倾向
